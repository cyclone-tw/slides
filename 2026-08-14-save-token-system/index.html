模型工程

Token / 成本 / 延遲 / 品質 四種預算

本頁主張：四種預算各自有不同 KPI，不可互相替代。

理解任務：標記每個決策會打在哪個預算上。

  • Token 預算：上下文大小、重複敘述、訊息往返。
  • 成本預算：模型單價＋工具呼叫次數。
  • 延遲預算：排程等待、重試、路由切換。
  • 品質預算：正確性、可讀性、可追溯性。

Token 下降不等於成本一定下降；品質也不是可以免費犧牲的預算。

情境治理

Before / After：熱溫冷 Context

Hot

Code Review

Review 不是直接省 Token

本頁主張：獨立 Reviewer 會增加一輪 Token；價值是避免更大的返工。

理解任務：比較「晚發現問題」與「受控 review gate」的成本路徑。

問題晚發現

成本不確定
Coding→Merge→晚發現問題→Debug／Rollback／重審

受控 Review Gate

最多 2 輪
Coding→Exact-SHA Review→修正→Merge

Review 是可控的保險成本，不是免費的 Token 優化。[S7]

Review Guardrails

你的 Review 架構在哪裡止血

本頁主張：五道限制把「重審循環」控制在明確邊界內。

理解任務：指出每道限制避免哪一種重複工作。

01Exact base／HEAD只審指定版本
02Review 期間凍結不 push 移動目標
03Coder ≠ Reviewer新 context 獨立檢查
04Round 2 同 lane不用重新熟悉背景
05最多 2 輪超過即停止循環

避免 stale review不審過期 SHA

避免 context 重建Round 2 不換 Reviewer lane

避免流程過度低風險 docs／typo 走 fast path

這些設計省的是「重複 review 與返工」，不是取消品質 gate。[S7]

理解任務：用同一公式比較每個完整任務。

目前 ledger 多筆為 n/a；現階段只能解讀單一 A/B，還不能宣稱全系統省了多少。[S3]

驗證

7 天實驗

本頁主張：最短周期先證明主線影響，非追求一次到位。

理解任務：跑 7 天 A/B，一次只改一個變因。

Day 1 至 2：選 5 個可重複任務，記 baseline。

Day 3 至 5：只改一項，例如縮短 AGENTS 或過濾 tool output。

Day 6 至 7：比較 input、cached input、output、tool bytes、延遲與返工。

驗收條件：至少一項明顯改善，其他指標不得越過事先設定的退步門檻。

結論 / Q&A

結論

本頁主張：少載入才省 Token；model routing 省單價；review 避免返工。

理解任務：選一個直接節流槓桿，先做可量測實驗。

省 Token 的順序：少載入 → 少取回 → 少帶 raw output／歷史 → 再控制返工。
