03 Sandy

珊迪：把收藏資訊轉成個人化知識

珊迪的痛點很清楚：收藏當下覺得有用，但幾天後就忘了；如果沒有輸出與應用，收藏最後只是資料堆積。

珊迪

核心流程

珊迪設計一套收藏 agent 工作流。使用者在 Discord 貼連結或文字，agent 讀取內容後做第一次整理，先存入 Obsidian 作為原始知識倉庫。每天晚上，agent 會整理當天收藏重點並提出三個簡單問題；隔天早上再提出更深層問題，讓使用者思考「這個資訊可以用在我哪些情境？」

使用者回答後，agent 會把原文重點與個人回答整合，輸出成個人化心得，放入系統 inbox，成為之後能複習、能拿出來用的材料。

收藏知識轉化圖

輸入Discord 貼連結、貼文字、丟待收藏內容。
初整agent 抓取內容，萃取重點，先放 Obsidian。
提問晚間複習題、隔日深度問題，促進消化。
輸出整合成個人化心得，放入 Notion / inbox。
1. Discord 入口用最自然的方式把資料丟給 agent。
2. 初步摘要長文、文章、連結先轉成可讀重點。
3. Obsidian 倉庫原始整理主要給 agent 回讀。
4. 早晚問答透過提醒與提問把收藏變成思考。
5. 個人化心得最後輸出到可複習、可使用的位置。

踩坑：需求一開始太模糊

最初只是想「丟連結就收藏」，後來才逐步釐清資料從哪裡來、存在哪裡、誰讀取、最後輸出到哪裡。她的做法是把最終目的告訴 AI，讓 AI 反問還需要哪些資訊。

踩坑：部署環境不一致

本機、Windows、Zeabur / VPS、Hermes agent 安裝環境不同，讓初期卡關。她的結論是：開發環境要盡量貼近部署環境，先研究 runtime、套件、權限與伺服器需求。

踩坑：debug 不能只看單點

Discord bot 不回、Notion 欄位對不上、Cron job 沒跑，不一定是某個工具壞掉，而是整條資料鏈缺 token、權限、schema 或環境變數。

安全原則：GitHub 可以保存開發歷程與 debug 紀錄，讓未來 agent 回讀；但 .env、API key、token、private key 不能推上 GitHub。這條規則要寫進 AGENTS.md 或其他 agent 工作規範。
04 Tiffany

Tiffany：多 agent、部落格與生活自動化

本段依 Notion 逐字稿中的「Tiffany分享」整理，以下統一使用 Tiffany。

Tiffany

分享主軸

Tiffany 分享自己做 agent 約兩三個月，剛好搭上共學團，因此把個人探索與共學成果一起整理。他一開始以為要讓 agent 24 小時跑，就需要買 Mac mini 或常開主機；後來改用 VPS / 雲端伺服器，透過 SSH 與部署流程把專案放上去。

他也反思：如果把每個規則都寫死，agent 只會照規則執行，失去「代理人」能學習、進化、突破使用者盲點的價值。因此後來調整 skill 與 workflow，保留彈性，讓 agent 能逐步貼近他的行為模式與期待。

多 agent 工作流

Wisp agent管理生活、行事曆、Notion 任務、提醒、體重飲食與 AI 資訊。
部落格工作流用 AI 協助改 Ghost 主題與部落格視覺，降低付費模板成本。
N8N 發文流程協助文章推送到 Threads、Instagram、Facebook 等平台。
模型切換架構透過 OpenAB / Open App 類工具，避免被單一模型綁住。

生活與副業管理

Wisp agent 可協助建立 Google Calendar 行程、管理 Notion 任務、做十分鐘提醒，也追蹤體重、運動量、卡路里、飲食與 AI 市場消息。

部落格與動機設計

他重視部落格視覺與季節感，不想花 80 到 100 多美元買 Ghost 付費主題，因此讓 AI 協助從免費模板改成自己想要的樣子。這不只是外觀，而是讓自己有動力持續寫。

N8N 不熟也能推進

雖然上過 N8N 課程但仍不熟操作，他改成讓 agent 協助建流程。重點不是自己多會用工具，而是能不能指揮 AI 幫自己操作工具。

踩坑與解法

  • 硬體門檻：24 小時運作不一定要買本地設備，VPS / 雲端伺服器能降低初期門檻。
  • 規則過滿：規則寫太死，agent 會失去代理人價值；要保留學習與修正空間。
  • 模型額度變動：訂閱方案或 token 額度改變，會迫使架構重構；因此要避免被單一模型綁住。
  • 法律與授權：部落格 footer 應補隱私權、法律聲明與內容授權，避免內容被盜用時缺少基本保護。
05 Zhijie

志傑：從功能膨脹到減法工作流

志傑的分享把重點拉回「真正有用」。不是每個工作流都需要 agent，也不是每件事都值得用 AI。最好的自動化，通常是直接打中每天或每週反覆發生的痛點。

志傑

從想做很多，到只做最痛的事

志傑一開始也受大家成果刺激，想做很多功能：OpenClaw、Claude Code、Hermes、提醒、Google Calendar、中央氣象局 API、網頁管理等都嘗試過。但做完後發現，很多功能每天使用不到一次，於是開始問自己：「我真正需要的是什麼？」

最後他回到工作痛點：現場拍照記錄後，要花大量時間整理照片、建立資料夾、分類並後續管理。原本想用 AI 圖片辨識浮水印、改檔名、寫入 Notion，但估算後發現成本太高，而且相機 app 本身已能把關鍵資訊寫進檔名，因此不需要 AI 辨識。

照片分類 App 的減法

原本想法AI 辨識照片浮水印，改檔名、分類、寫入 Notion。
成本估算每月數百到上千張照片，AI 辨識成本可能到數千元。
關鍵發現相機 app 已能把資訊寫入檔名，不必再辨識一次。
最終工具一鍵依檔名規則分類照片到正確資料夾。
1. 現場拍照工作現場大量照片，檔名已有可用資訊。
2. 帶回整理原本要手動建資料夾與分類。
3. 成本盤點確認 AI 辨識不是必要解法。
4. 一鍵分類App 依檔名規則自動分到資料夾。
5. 節省時間400 多張照片約 5 分鐘完成。

踩坑：為了用 agent 而用 agent

一開始嘗試很多 agent 與提醒，但使用頻率低。真正有效的是回到工作中反覆發生、且能明確省時間的痛點。

踩坑：AI 解法成本過高

AI 圖片辨識看似完整，但每張照片都有成本；若每月七八百張甚至上千張，花費會快速累積。先找低成本替代方案更實際。

開發方式：GPT 規劃，人類決策

由 GPT 幫忙規劃，志傑做決策刪掉不必要部分，再交給 Claude / Codex 實作，用 GitHub issue 記錄需求與開發過程。

志傑這段的核心：工具不需要華麗，能反覆使用才重要。AI 工作流的第一個問題不是「能不能做」，而是「這件事真的需要 AI 嗎？」
06 Cyclone

Cyclone：個人 dashboard、Hermes agents 與 GitHub 開發流程

Cyclone 分享的核心是把多個系統接成一條可管理的工作流：個人 dashboard、共學網站、Hermes agents、OpenAB、GitHub issue / PR / code review，以及未來的文書輸出 pipeline。

Cy

從工具堆疊到工程流程

Cyclone 近期主要維護五個 GitHub repo，包含個人 dashboard、共學網站、Hermes agents、OpenAB / Open App 類工具，以及其他與資料流相關的專案。重點不是 AI Coding 很快，而是 AI Coding 讓他開始用更工程化的方式管理需求、issue、PR、review 與部署。

即使很多 code 看不懂，也能透過 issue / PR 來確認需求是否被實作，並讓 OpenAB 做第二道 code review。這些紀錄也不只是給人看，未來 agent 可以回讀它們，知道哪些做完、哪些沒做、卡在哪裡。

07 Insights

共通洞察

1. 資料流比工具數量重要

珊迪強調資料從哪裡來、存在哪裡、誰讀取、輸出到哪裡；Cyclone 的 pipeline 也在處理同一件事。工具只是節點，資料流才是系統。

2. 真實痛點決定工作流價值

志傑的照片分類 App 有價值，因為它直接省下大量整理時間。不是每個功能都值得做，使用頻率與節省時間要先算。

3. 減法與彈性要同時存在

志傑提醒要減法，Tiffany 提醒 agent 不能全寫死。減法降低使用摩擦，彈性讓 agent 有進化空間。

4. GitHub 是 agent 的記憶層

issue、PR、commit、debug 紀錄不只是工程儀式；它們能讓未來 agent 知道專案歷史、未完成工作與風險。

5. 不熟工具也能讓 AI 操作工具

N8N 案例顯示，能力重點從「熟悉每個工具介面」轉向「能清楚指揮 AI 幫自己操作工具」。

6. 安全規則要先寫

所有流程都會碰到 token、API key、VPS、GitHub、Discord、Notion。禁止提交 .env 與 private key 應成為共學團預設規範。
